Saya menggunakan mode build, jadi kamu boleh langsung mengubah kode. Namun sebelum mengubah, lakukan audit internal terlebih dahulu terhadap alur generate awal dan endpoint replace. Setelah menemukan masalahnya, revisi hanya bagian yang berkaitan dengan EDAS, preference mapping, replacement selection, dan durasi. Jangan mengubah UI, NLG, database schema, atau fitur platform eksternal kecuali benar-benar diperlukan. Setelah selesai, jalankan npx tsc --noEmit dan berikan ringkasan file yang diubah, masalah yang ditemukan, serta panduan tes manual.

Saya ingin melakukan revisi kecil pada project, bukan perubahan besar. Tolong kerjakan dua hal saja:

1. Tambahkan aturan kelayakan kandidat lagu berdasarkan durasi minimal.
2. Tambahkan komentar dokumentasi pada kode penting untuk kebutuhan penjelasan paper.

Jangan mengubah UI, NLG, schema database, rumus EDAS, preference mapping, atau logika utama yang sudah berjalan, kecuali benar-benar diperlukan untuk menerapkan filter durasi minimum.

Konteks:
Project ini adalah sistem rekomendasi playlist musik berbasis konteks aktivitas pengguna menggunakan metode EDAS. Saat ini generate awal dan fitur ganti lagu sudah memakai EDAS. Fitur ganti lagu menggunakan opsi replacement reranking, yaitu menghitung ulang kandidat yang tersedia setelah mengecualikan lagu yang sudah ada/excluded, lalu memilih pengganti berdasarkan Appraisal Score dan gap durasi.

Masalah kecil yang ingin diperbaiki:
Ada beberapa lagu yang durasinya terlalu pendek, misalnya di bawah 90 detik, tetapi bisa muncul di ranking atas karena sangat cocok secara parameter audio. Secara EDAS ini tidak salah, tetapi untuk kualitas playlist aktivitas, lagu yang terlalu pendek bisa terasa kurang representatif. Karena itu saya ingin menambahkan filter durasi minimum.

Permintaan 1 — Filter durasi minimum:
Tambahkan aturan bahwa kandidat lagu yang digunakan untuk generate playlist awal dan fitur ganti lagu harus memiliki durasi minimal 90 detik.

Aturan:

* Durasi minimal: 90 detik atau 90000 ms.
* Terapkan pada generate awal.
* Terapkan juga pada endpoint replace/ganti lagu.
* Jangan ubah struktur database.
* Jangan ubah rumus EDAS.
* Jangan ubah mapping kuesioner.
* Filter ini diposisikan sebagai tahap penyaringan kandidat lagu sebelum EDAS/playlist selection, bukan sebagai bagian dari rumus EDAS.
* Jika ada konstanta, buat jelas, misalnya `MIN_PLAYLIST_SONG_DURATION_MS = 90_000` atau `MIN_PLAYLIST_SONG_DURATION_SEC = 90`.
* Lebih baik gunakan konstanta supaya nanti mudah dijelaskan di paper.
* Pastikan lagu di bawah 90 detik tidak masuk playlist awal dan tidak masuk hasil replacement.

File yang kemungkinan perlu dicek:

* `frontend/src/server/modules/dummyPlaylist.ts`
* `frontend/src/app/api/recommendations/replace/route.ts`
* `frontend/src/server/utils/edas.ts`
* file route `/api/dummy-playlist` jika ada
* file lain yang mengambil kandidat lagu dari tabel `songs`

Implementasi yang saya harapkan:

* Jika filter dilakukan di query database, ubah `where duration_ms > 0` menjadi `where duration_ms >= 90000`.
* Jika lebih rapi memakai konstanta, gunakan konstanta agar tidak ada magic number.
* Pastikan filter berlaku konsisten di generate awal dan replace.
* Jangan filter data pada tabel database secara permanen; cukup filter saat runtime kandidat rekomendasi.

Permintaan 2 — Komentar dokumentasi kode:
Tambahkan komentar kode untuk bagian-bagian penting agar nanti bisa dipakai untuk memahami snippet paper. Komentar cukup menjelaskan fungsi blok kode, bukan komentar berlebihan pada setiap baris.

Tambahkan komentar sebelum blok kode penting seperti:

* normalisasi jawaban kuesioner,
* mapping jawaban ke bobot dan jenis kriteria,
* perhitungan average solution,
* perhitungan PDA/NDA benefit dan cost,
* perhitungan neutral jika ada,
* normalisasi SP/SN,
* perhitungan Appraisal Score,
* ranking EDAS,
* selection playlist berdasarkan target durasi,
* filtering durasi minimum,
* replacement selection berdasarkan gap durasi,
* debug EDAS development-only.

Syarat komentar:

* Komentar boleh dalam bahasa Indonesia.
* Komentar harus singkat dan akademik.
* Jangan mengubah kode berjalan hanya demi komentar.
* Jangan mengubah nama function/variable jika tidak perlu.
* Komentar ditambahkan sebelum blok/fungsi penting, bukan mengotori semua baris.

Permintaan 3 — Jangan hapus debug:
Mode debug EDAS dan replacement yang sudah dibuat jangan dihapus. Debug ini masih saya perlukan untuk audit dan mungkin akan menjadi bahan penjelasan paper. Pastikan debug tetap development-only.

Catatan metodologis:
Jika nanti ditulis di paper, filter durasi minimal 90 detik akan dijelaskan sebagai aturan kelayakan kandidat lagu agar playlist tidak didominasi potongan lagu yang terlalu pendek. Ini bukan perubahan rumus EDAS.

Output akhir yang saya butuhkan:

1. File apa saja yang diubah.
2. Di mana konstanta durasi minimal diletakkan.
3. Apakah filter 90 detik berlaku untuk generate awal dan replace.
4. Apakah rumus EDAS berubah atau tidak.
5. Apakah debug EDAS tetap ada.
6. Ringkasan komentar dokumentasi yang ditambahkan.
7. Jalankan:

   * `frontend\node_modules\.bin\tsc.cmd --noEmit`
   * `npm run build` dari folder frontend jika memungkinkan.
8. Berikan panduan tes manual singkat.

Panduan tes manual:

1. Jalankan generate awal dengan target 30 menit.
2. Pastikan tidak ada lagu berdurasi di bawah 1:30.
3. Jalankan debug endpoint dan cek top playlist.
4. Ganti 1 atau beberapa lagu.
5. Pastikan replacement juga tidak menghasilkan lagu di bawah 1:30.
6. Pastikan total durasi playlist tetap mendekati target.
7. Pastikan UI, history, NLG, dan export tetap normal.
